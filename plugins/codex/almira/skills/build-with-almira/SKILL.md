# Build With Almira

Add storage to the user's application; do not treat Almira as an application builder, deployment system, or end-user product. The coding agent owns edits and its host owns approvals. Almira only authorizes each management request with the user's scoped Metamorph PAT or SAK.

## Set Up Resources

1. Inspect the application, its framework, and its existing authentication before changing code.
2. Call `metamorph_sign_in_start`, show or open its `authorization_url` through the host, and call `metamorph_sign_in_complete` until it reports `authenticated`. Never ask for or expose the device key, poll secret, or native bearer; they remain inside the product-neutral Metamorph MCP process.
3. Call `metamorph_tenant_get`, `metamorph_space_list`, and `metamorph_project_list` with `product_id: "almira"`. Select the project that matches the inspected application and user intent. If none is suitable, call `metamorph_project_create` with the Tenancy-owned tenant/default-space facts and an explicitly selected advertised region; do not fabricate any ID or move project authority into Almira.
4. Call `metamorph_project_get` after selection or after creation reaches active state. Pass its exact successful Tenancy response as `tenancy_project` to `almira_project_bootstrap`, together with `tenant_id` and `project_id`. Almira reauthorizes the snapshot, converges the managed `development` and `production` environments, and is safe to retry with the same `operation_id` after an ambiguous outcome.
5. Call `almira_environment_list` and use the managed `development` environment unless the user explicitly requests another environment. Use `almira_environment_create`, `almira_environment_update`, and `almira_environment_delete` for additional lifecycle needs. A project may contain up to ten environments; the managed `development` and `production` defaults cannot be deleted.
6. Call `almira_storage_capabilities_get` for the selected environment before choosing storage configuration. Treat realization IDs as opaque and select only advertised `normal` or `express` targets. The catalog may include current-model targets plus project-approved migration targets from another operating model; collection creation uses the environment's current model. Never request or place provider buckets, endpoints, or credentials in application configuration.
7. Call `almira_collection_list`. Reuse a suitable collection or call `almira_collection_create` with the selected advertised `storage_class` and an explicit `malware_scan_required` choice. Never infer that scanning exists when it is not configured. Keep the default 30-day recycle window unless the application needs another value; `almira_collection_lifecycle_replace` accepts 1–3650 days with the current collection revision, affects future deletions only, and does not perform physical purge.
8. Read `almira_collection_protection_get` before changing an existing collection's malware policy. `almira_collection_protection_replace` affects only new generations. Use `almira_protection_cases_list` for environment-wide safe status, and request an exact-generation `almira_protection_rescan` when needed. A rescan immediately removes that generation from delivery until FileService returns a clean verdict. Reviews are content-free audit records: `almira_protection_review_create` can mark a blocked result as confirmed or suspected false-positive, but it never releases content or overrides FileService. There is intentionally no release tool.
9. When the user asks for a compliance-oriented storage configuration, call `almira_compliance_profile_list` and `almira_compliance_profile_preview` first. Show exact blockers, effects, customer responsibilities and the non-certification notice. Activation and removal use the host's normal approval flow and retained operation IDs. Never describe a technical profile as certifying the application or organization, infer legal approval from the GDPR declaration, or represent profile activation as reviewed claim admission; claim publication remains gated by the reviewed CMP catalog and owner/provider evidence.
10. To change an existing collection's storage class or operating-model realization, require a `ready` collection and an advertised target, then call `almira_storage_migration_start` with the collection revision and exact target class/generation; retain its operation ID. Do not create a replacement collection or choose a provider target. Uploads to that collection pause while migration is active. Retry an ambiguous start with that same operation ID even if the collection now reports `migrating`; it exactly replays instead of starting another migration. Poll `almira_storage_migration_get` until `succeeded` or `failed`; report the durable phase, progress and stable failure instead of assuming the start response means completion. To leave customer-owned storage, migrate every collection to current managed targets first, then call `almira_storage_restore_managed` with the environment revision. Never call the final transition while a migration is pending.
11. Use `almira_collection_import_start` only with a FileService-issued opaque source binding and bounded safe manifest; never request cloud credentials, buckets, endpoints, or a target realization. For each declared object, call `almira_portability_import_upload` with its source-object UUID and existing local path; reuse the same operation ID and unchanged file after an ambiguous result, and never place file bytes in the prompt. Follow imports and exports with `almira_portability_jobs_list` and `almira_portability_job_get`. Start portable exports with the current collection revision. When bytes are needed locally, use `almira_portability_export_download` with a new path; it verifies size and SHA-256 without returning the one-use bearer to the model and refuses overwrite.
12. Read `almira_collection_extraction_get`, including its exact versioned media-type and resource policy. Safe technical metadata is always on. Enable content extraction, OCR, transcription, or vector indexing with `almira_collection_extraction_replace` only when the application needs it and its media fits that policy. Vector indexing requires content extraction. Raw extracted content is separately authorized and must not be copied into ordinary metadata, logs, or prompts.
13. Read `almira_collection_media_get`. Configure bounded image presets, document previews, or `web_hls_v1` with `almira_collection_media_replace` only when the application needs those outputs. Use processing-job tools for status/retry/cancel and preserve the job revision. Treat derivative variant keys as opaque Almira names, never provider paths or URLs.
14. For browser-to-storage transfers, read the current policy with `almira_browser_origins_get`, preserve its revision, and replace it with `almira_browser_origins_replace`. Add only exact application origins.
15. Before integrating application credentials, derive the real deployment subject and audience from the inspected application/deployment and use only a catalog-admitted attestation rule. Call `metamorph_workload_identity_list`; reuse an exact suitable project binding or call `metamorph_workload_identity_create`, then verify it with `metamorph_workload_identity_get`. Never invent an attestation rule, copy a developer PAT/SAK into the workload, or ask Almira to own the Identity binding.

For repeatable setup, prefer a checked-in `almira.yaml` v1 document. Call `almira_configuration_preview` first, show its exact additive actions and conflicts through the host's normal approval UX, then call `almira_configuration_apply` with one retained root `operation_id`. Existing recycle-retention, malware-policy, extraction, media, and class changes are applied in one revision-safe sequence; a class change starts the same governed migration and its receipt must still be followed to terminal state. Unlisted resources are preserved; do not describe apply as pruning or deployment.

Reuse the returned `operation_id` when retrying any mutation whose result was not received. Let the host request approval normally; do not introduce a second plan or approval protocol.

## Integrate The Application

Use `@metamorph-labs/almira-sdk` instead of hand-written HTTP calls. Instantiate `AlmiraClient`, create a transfer with `createUpload`, send bytes with `uploadDirect`, and commit the generation with `finalizeUpload`. Use `readPrivateFile` for authorized reads. Follow the SDK README and the executable Node/Next.js route example in `examples/node-upload` when available in the checked-out Almira repository.

Treat a file entry as the stable identity and generations as immutable bytes. For lifecycle work, use the published `createFileVersion`, `listFileGenerations`, `renameFile`, `restoreFileGeneration`, `deleteFile`, and `restoreFile` SDK methods or their management tools. Deletion must be treated as immediate read refusal even though a management caller can restore the entry during its bounded recycle window.
For multiple independent lifecycle mutations, prefer `mutateFilesBatch`/`almira_file_batch`: it is atomic, revision-bound, limited to 100 actions, and accepts each entry only once.

Use `copyFile`/`almira_file_copy` for an exact-generation server-side copy. It creates an independently owned object at a new collection-local path, carries customer metadata, reapplies the destination collection's current safety policy, and never sends bytes or provider credentials through the coding agent.

Use `replaceEntryMetadata` or `almira_file_customer_metadata_replace` for bounded customer tags and scalar fields. Use authoritative list filters for exact lifecycle, tag, metadata, media-type, size, time, and extraction-state queries. Read `almira_file_extraction_get` for safe exact-generation status; request `almira_file_extracted_content_get` only when the user's token has the distinct permission and the application genuinely needs the protected text.

Use `searchFiles` or `almira_file_search` for lexical search. Use semantic or hybrid mode only after the collection explicitly enables content extraction and vector indexing. Treat search as eventually consistent: lag can reduce recall, while Almira rechecks every candidate against current lifecycle, generation, safety, metadata, and authorization authority before returning it.

Use `listGenerationDerivatives` for management metadata and the capability-only `AlmiraDataClient.listDerivativesWithCapability` and `readDerivative` paths in the builder application. Do not construct provider URLs. HLS manifests contain same-generation relative variant references so each segment stays behind Almira authorization, source-safety and CDN policy.

Keep the Almira product origin in `ALMIRA_BASE_URL` (without a `/platform/almira` prefix) and an `mm_pat_v1.` PAT or `mm_sak_v1.` SAK in `METAMORPH_TOKEN`. Never write a PAT, SAK, workload credential, one-use upload URL, or upload header into source, logs, prompts, or generated documentation. Deployed applications must use short-lived customer-workload evidence from Metamorph Identity, not a developer PAT or SAK.

Do not provision S3, GCS, or Azure credentials in application code. Almira owns provider placement, delivery, safety processing, metadata extraction, and CDN behavior behind its API.
Configure an optional collection custom hostname only through Almira's delivery operation. Use the returned provider-neutral CNAME target and ownership challenge; never configure CDN credentials or call a CDN provider directly. Send `custom_hostname: null` to keep the managed hostname. When a collection-wide invalidation is needed, call `almira_delivery_purge_create` once with a retained operation ID and verify its asynchronous result through the delivery read. That read exposes the 20 newest provider-neutral cache-invalidation diagnostics; use those states without seeking a provider receipt or privileged endpoint.

## Verify The Journey

Write the application code and automated tests first. Then upload a non-sensitive canary of at most 8 MiB through the application path and retain the transfer ID, completion evidence, exact finalize operation ID, entry and generation. Call `almira_verification_receipt_create` with those values and a distinct project environment as the refusal target. Almira itself replays finalization, hashes the exact private read, requires the cross-environment refusal, and checks the configured malware gate before signing the resource- and contract-bound receipt. Verify the Ed25519 signature and exact expected resource binding with `verifyReceiptWithClient`; a valid signature for another resource is not success.

Resource creation alone is not success. Do not invent a client-side success receipt, treat an unsigned assertion as proof, or use this bounded canary operation for files above 8 MiB. Report exactly what was tested and any check that could not run; do not claim that Almira built or deployed the application, and do not claim compliance certification.
